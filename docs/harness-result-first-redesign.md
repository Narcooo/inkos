# 从创作结果重新审视 Harness

2026-09-10。授权目标：创作结果和用户交互流畅度优先，允许替换不合适设计。本轮不以现有模块数量、测试数量或某个模型一次成功作为设计正确的依据。

## 判断

部分问题确实由 Harness 设计带来，而且不只是提示词不够严格。它把通用文件工具、领域生产工具和前端显示数据拼在一起，但给主模型的接口没有形成一致的作品、版本和结果语义。模型因此承担了路径转换、结果解释和继续执行状态的推断。重复添加“不要猜”“不要误报”只能降低偶发率，不能消除这类任务。

仍然需要分开判断三类问题：通用DeepSeek名称的实际路由失败有网关/上游证据；稿件因果和商业回报问题需要生产方法与审稿证据；跨作品、越界修订、版本选择和状态恢复是系统责任。不能把模型API兼容性或市场质量全归因于Pi主循环。

## 本轮重构边界

交付一个跨类型纵向闭环：当前Work上下文给出可直接调用的读取目标 → Harness read → 已采纳版本/显式候选 → 校验与分页 → 结构化观察 → 压缩进度。脚本、分镜、翻译、短篇及其他登记文本均用同一边界。导出复用同一个版本读取器。

没有再增加一个与read重叠的“智能读取”工具。现有read接口获得产物寻址；路径形式保留给上传素材、项目文件和旧调用。旧的纯文本回执拼接逻辑已被替换，不与新协议并行。现有UI详情及Episode原始回执继续保留，避免把模型观察变成第二份领域数据库。

这不是全部Harness重构完成。实际创作质量、模型的首次完成率和浏览器交互仍需真实重跑；当前测试只证明模块合同和状态边界。特别是“Episode completed”表示本轮循环结束，不代表作品交付通过，验收不能再从这个字段推断成功。

## 验证方式调整

1. 每个结构性变更先走短小的真实模块闭环：正确Work、正确版本、范围保护、失败后恢复。避免按13类复制同一个实现断言。
2. 用历史真实回执复放检查观察信息损失和体积，不调用模型，不冒充真实用户成功率。
3. 获得数据外发许可后，先跑有代表性的真实旅程：线性创作与局部修改、跨Work派生、互动状态与正文修改。记录用户补充次数、模型失败次数、重复读取、误改和端到端耗时。
4. 这些代表旅程稳定后才冻结候选做一次完整13类发布验收；不为每个局部修复从头跑整张矩阵。
5. 内容硬伤遵守系统审稿与人读双确认；审美偏好和单次失败不得直接变成全局提示词规则。商业质量与真实市场效果分别判断。

## 多篇来源的创作边界（2026-10-09）

真实同人任务要求使用已登记的前三章，创建动作却只能传入一份来源引用，最终绑定了第一章；后续设定提取与审稿继承了这个缩窄后的输入。创建同人、番外、风格仿写与按 Profile 创建作品现支持有序来源集合，保留每份原文与确切版本。恢复时继续使用已绑定版本，来源集合或版本改变则返回冲突。单份来源调用保持兼容，显式来源也不会被上传附件的自动补全覆盖。

## 审稿发现与交付完成（2026-10-10）

原战略审查 F7 要求质量反馈不变成自动重写门。C42 的真实执行再次暴露了这条边界的重要性：专业审稿既能发现重复归还钥匙等真实缺陷，也会把赠予与借款混算、把角色拒绝规则当成叙事矛盾。整篇改稿诊断中的审稿还把“多件作品”与“第一件自己满意的作品”判为数量矛盾。把每条 `quality/issue` 一律变成交付阻断，会要求主模型修正文稿或说服另一轮审稿撤回意见，重新形成自动重写门。

交付检查现在只证明对应操作和硬约束：请求的审稿与导出已执行、来源版本一致、导出未过期、明确篇幅或必需产物满足、作者修改范围得到保护。专业质量意见仍按作品、产物与版本保留；有未解决意见时，完成回执带上原始发现，用户可见答复附上意见摘要。主模型负责核对依据、执行请求范围内的必要修订，并如实说明剩余问题；`delivered` 不代表内容质量或市场效果获得认证。仅用于启动旧质量门的新稿分类已从操作提取中删除，旧会话里的分类字段只保留为历史证据。

另一项独立修复是批量审稿来源绑定：C42 第3章的发现曾同时挂到第1、2章，导致修复第3章后仍被旧意见阻断。绑定在操作回执形成时依据实际章节分组和已核验版本完成，不能由模型解释文本来推断归属。即使质量意见不再作为硬门，这项绑定仍用于正确呈现、复审和追踪。

发布验收继续分为两层。Harness 验收检查真实 Studio 创作、修改、恢复和交付；Content Benchmark 独立核对完整故事、已确认硬伤、封面和销售包装。完成状态、意见条数为零、模型自称合格均不能替代内容验收。现有冻结候选的失败和读稿记录保留，新行为必须在后续同一冻结候选上重新验证，不将旧候选改判为通过。
